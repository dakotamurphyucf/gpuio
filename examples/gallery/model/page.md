# Page: typed navigation identity, labels and stable keys

[page.ml](page.ml) and its [interface](page.mli) define the gallery's 24 section
identities and display metadata. This is a pure finite catalog, not a router,
Bonsai state machine, window owner or resource scope. A title describes a section;
a typed variant and its key identify it independently of label or list position.

From the repository root:

```sh
GPUIO_JOBS=2 ./scripts/gpuio build examples/gallery/main.exe
./scripts/gpuio exec _build/default/examples/gallery/main.exe
```

Click any section in Component Studio's navigation. There is no separate Page
executable, asset or diagnostic flag. Toolchain prerequisites are in
[development](../../../docs/development.md); documentation review does not qualify
native keyboard, accessibility or platforms.

Read the closed `type t`, `all`, `title`, `description`, then `key`. The public
variant ranges from Presentation through Runtime, with typed equal/compare/sexp_of
functions generated by Jane Street PPX. `all` is explicit navigation order rather
than a numeric enum encoding. `title` supplies displayed headings/buttons and
`description` their help text. `key` supplies stable strings such as `charts`,
`text-inputs` and `documents`; it does not parse arbitrary strings into Page values.
There is no mutable state or default page in this module.

[application.ml](../application.ml) creates a window-local Bonsai Var initially
Presentation. [component.ml](../component.ml) reads its reactive value and supplies
`Shell.Actions.select_page`, an effect that updates that Var. A reactive value
changes over time; an effect is work a handler schedules, not something executed
while constructing a view. [shell.ml](../shell.ml) uses `Page.all` for navigation,
`Page.equal` for selection, title/description for chrome and key for the
`preview-<key>` content wrapper.

[pages.ml](../pages.ml) contains `match%sub page`: Bonsai syntax for selecting an
active computation branch from the reactive variant. Each branch constructs its
actual page component. Page itself does not mount/unmount previews; branch
lifecycle and scoped native ownership do that. Choices retained by a branch can
survive revisits while native editors/documents/chart registrations are retired
according to their own component policies. A single Page value shared between
windows would not make those native resources share ownership.

For a concrete trace, click **Charts & data**. Shell's button runs select_page Charts;
the window's Var changes, `match%sub` activates Charts_page, and the shell derives
that section's heading/description and `preview-charts` key. Charts_page acquires
its scoped source asynchronously. Returning to Presentation deactivates the chart
branch and cancels its resources; it is the page component and scope helper, not
this catalog's key function, that release them. Follow the
[composition walkthrough](../component.md) and [routing walkthrough](../pages.md)
for graph construction/lifetimes.

To rename a section, edit title/description while retaining its variant/key.
To add a new section, extend both interface/implementation variants, navigation
`all`, all three exhaustive metadata matches and the router's exhaustive `match%sub`.
Use a unique stable key; reusing keys can confuse retained view identity, and
removing a section only from `all` would leave a router-only branch rather than
fully removing it. This model needs no native disposal or I/O cancellation.
